System Overview

Hindsight Financial is a client-server educational trading game. A Unity 6 client handles rendering, input, and local UI state. A .NET 10 backend owns all game logic, market data, and LLM orchestration. They communicate over HTTP on localhost:5000.

The architecture is server-authoritative: the client never computes prices, executes trades, or evaluates knowledge triggers. It sends intents ("queue a buy of 10 AAPL") and receives results. This matters for two reasons: (1) academic integrity in a classroom deployment — students can't cheat by modifying the client, and (2) the adaptive systems (knowledge graph, LLM content) need access to the full game state, which lives in a SQLite database the server owns.

Three external dependencies exist: Yahoo Finance (historical OHLC data for 250 symbols, downloaded once at DB init), Claude API (Anthropic, for generating newspapers, NPC dialogue, and personalized educational content), and Puppeteer (headless Chrome, renders newspaper HTML to PNG for in-game display).

Why This Split?

The alternative was a monolithic Unity build with embedded SQLite — simpler to deploy but architecturally dead-end. The REST API means:

  • A future web client (React, etc.) hits the same endpoints with zero backend changes
  • A teacher dashboard is just another API consumer
  • LLM orchestration happens server-side where you have full DB access, not in the Unity process where you'd need to serialize everything across the managed/native boundary
  • The knowledge graph evaluation can access all entity state in a single transaction — no round-trips to the client

The tradeoff: startup complexity. The Unity client runs an APIBootstrapper sequence on scene load (launch backend process → ping → init DB → load tickers → register entity → init knowledge graph → sync game state). In Editor mode, the backend runs separately; in builds, BackendProcessLauncher spawns the .exe as a child process.

End-to-End Data Flow

Understanding how a single game day flows through the system clarifies how all the pieces connect. Here's the full lifecycle of one day, from the player waking up to sleeping.

AdvanceDay completes → PRE-MARKET begins

Backend sets game_phase = pre_market in save_state. Returns the new date and today's open prices. Unity's GamePhaseManager fires OnPhaseChanged, which triggers NPCBark.RefreshDialogue(date) — this kicks off the dialogue generation pipeline (POST then GET to /dialogue endpoints).

Player queues orders

Orders are queued locally in GamePhaseManager.LocalPendingOrder[] then batch-sent via POST /queue_order. Backend validates and stores in pending_orders table. When player confirms, POST /open_markets executes all pending orders at today's open price. Backend updates portfolio (FIFO lot tracking), trade_history, entity.available_cash, and invalidates the PlayerContext cache.

DAY phase — timer countdown

Client-side timer runs. Player explores the city, walks near NPCs (proximity triggers barks from the pre-fetched dialogue pool), can open the knowledge graph terminal, read the newspaper. No server calls unless explicitly triggered (e.g., viewing newspaper calls GET /newspaper which may trigger Claude generation + Puppeteer render if not cached).

Timer expires → POST-MARKET

Same order flow as pre-market, but POST /close_markets executes at today's close price. DailySummaryOverlay shows P&L, movers, portfolio state. After trade execution, backend checks knowledge graph triggers.

Knowledge trigger evaluation

Client calls GET /knowledge_graph/check_triggers. Backend's KnowledgeGraphService.EvaluateTriggers(entityId, date) runs all 13 evaluators against current state. Any that pass: node status updated to "unlocked" in knowledge_node_progress. If DynamicNodeContentService is available, it generates a personalized explanation via Claude using PlayerContextService.BuildContext(). Results returned to client → UI notification.

Player sleeps → AdvanceDay

POST /advance_day increments the date in save_state, checks for arc boundary crossings (if date > arc.EndDate → trigger arc advance, grade calculation, cash multiplier). Returns new date. PlayerContextService cache invalidated. Cycle repeats.

Key insight: The PlayerContextService cache is invalidated after trades and day advances — the two moments when player state materially changes. Between those moments, all three LLM services (dialogue, newspaper, node content) read from the same cached snapshot. This prevents N+1 queries: generating 4 NPC dialogues doesn't mean 4 separate portfolio lookups.

Service Architecture

The backend is structured as a set of singleton services registered via .NET DI in Program.cs. There's no repository pattern or ORM — services talk directly to SQLite via raw SQL (Microsoft.Data.Sqlite). This is intentional: the queries are game-specific enough that an abstraction layer would just add indirection without reducing complexity.

Service Responsibilities

PlayerContextService

The connective tissue. Assembles a canonical PlayerContext record from 6 sub-snapshots (portfolio, concentration, knowledge, trades, arc, market). Cached per (entityId, date) in a ConcurrentDictionary. Every LLM service consumes this instead of running its own state queries.

This is the architectural answer to "how do three independent LLM services all reference the same player state without duplicating SQL and risking inconsistency?"

NpcDialogueService

Generates contextual NPC dialogue. Unique behavior: interestingness gating — scores the current market day (0.0–1.0) using volatility, top movers, breadth, player events, and knowledge triggers. Only calls Claude if score exceeds threshold. This prevents burning API credits on boring days where static fallback lines are sufficient.

NewspaperService

Generates a daily newspaper article styled as "The Market Tribune." Prompt includes 52 real historical events (2007-2009) filtered by proximity to the current game date, market movers, arc tone, and now player portfolio context. Output is HTML, rendered to PNG via Puppeteer, cached in DB so each date only generates once.

DynamicNodeContentService

The thesis's strongest LLM feature. When a knowledge node unlocks, this generates a personalized explanation that references the player's actual portfolio state and the trigger that fired. Example: trigger portfolio_concentration fires → "You have 82% of your portfolio in NVDA. Here's why that's risky..." Cached per (entity, node) — only generates once per player per concept.

KnowledgeGraphService

Owns the knowledge graph definition (loaded from JSON config) and all 13 behavioral trigger evaluators. Each evaluator is a pure function: (entityId, gameDate) → bool. When evaluation returns true and the node's prerequisites are met, the node transitions from "locked" → "unlocked." Also handles mechanic gating (e.g., HasMechanic("limit_orders")).

OrderService

Manages the order lifecycle: queue → pending → execute. Supports market orders (execute at current phase price) and limit orders (execute only if OHLC range includes limit price). FIFO lot tracking for cost basis. On execution, invalidates PlayerContext cache and optionally triggers NPC dialogue regeneration.

GameStateService

Owns the save_state key-value table (current_date, game_phase, etc.), date advancement, phase transitions, and the dialogue query endpoint (UNION of static_npc_dialogue + dynamic_npc_dialogue filtered by date/type/phase).

ArcService

Defines the three story arcs (Bull Market, The Unraveling, Meltdown) with date ranges, grade thresholds, cash multipliers, and newspaper tone. Handles arc boundary detection and grade calculation. Optional dependency — game still works without arcs configured.

Dependency Direction

Dependencies flow downward: LLM services → PlayerContextService → Domain services → Database. No circular dependencies. The one quasi-circular pattern is OrderService invalidating PlayerContext cache after trades — but that's a cache invalidation call, not a structural dependency (OrderService doesn't read from PlayerContextService, it just tells it to flush).

PlayerContextService Deep Dive

Added 2026-05-31 to solve a specific problem: the three LLM services (dialogue, newspaper, node content) were each running their own portfolio/knowledge/trade queries independently. This meant duplicated SQL, potential inconsistency if state changed between calls, and no caching.

The PlayerContext Record

A single immutable snapshot composed of 6 sub-records, all built in one DB transaction:

SnapshotContentsUsed By
PortfolioSnapshotHoldings (ticker, shares, avg cost, price, P&L%), cash, net worth, cash ratioAll three LLM services
ConcentrationSnapshotMax single-ticker allocation %, which ticker, total position countNode content (diversification triggers), dialogue
KnowledgeSnapshotCompleted nodes, unlocked-not-completed, total count, recently unlocked todayDialogue (NPC can reference what you've learned), node content
RecentTradesSnapshotToday's trades, last 10 trades, total lifetime trade countDialogue (trader NPC references your activity), node content
ArcSnapshotCurrent arc name, days remaining, projected return %, grade, toneNewspaper (arc tone), dialogue (mood context)
MarketSnapshotTop 5 gainers/losers, advancing/declining counts, date/phaseNewspaper (market summary), dialogue (analyst/anchor content)

Caching Strategy

Cache key is (entityId, gameDate). A player's context doesn't change unless they trade or the day advances. The cache is a ConcurrentDictionary — thread-safe for concurrent requests but cheap since this is a single-player game (one entity, one date active at a time). Invalidation is explicit: OrderService calls InvalidateCache(entityId) after trade execution; GameStateService calls InvalidateCache() (all entries) after day advance.

In practice, a typical day hits the cache exactly once (first LLM service to build context), then all subsequent services read the cached snapshot. A day with 4 NPC dialogue generations + 1 newspaper + 1 node content = 6 reads of the same cached object instead of 6 independent query sets.

NPC Dialogue Pipeline

The dialogue system spans both codebases: the .NET backend generates and stores lines, the Unity client fetches and displays them. The pipeline has an intentional "quality gate" — the interestingness scoring system — that prevents calling Claude on boring market days.

Backend: Generation & Scoring

When Unity calls POST /dialogue/generate, the backend runs this sequence:

  1. Cache check — if dynamic_npc_dialogue already has rows for this (date, phase), return early. This prevents regeneration on scene reload.
  2. Interestingness scoring — evaluates 5 dimensions, each contributing 0.0–0.3 to a total score capped at 1.0:
    • Market volatility: average |close-prev_close|/prev_close across all tickers. Scores if avg > 1.5%.
    • Top movers: biggest single-stock move. 8%+ = 0.2, 5%+ = 0.1. Bonus if player holds the mover.
    • Market breadth: if 80%+ stocks moved same direction (broad rally/selloff).
    • Player events: trades made today, low cash ratio.
    • Knowledge triggers: if any triggers evaluated true this check (0.1 per trigger, max 0.25).
  3. Gating decision:
    • Score ≥ 0.5 AND API key present → generate all 4 NPC types (analyst, broker, trader, anchor)
    • Score ≥ 0.2 AND API key → generate analyst + anchor only
    • Score < 0.2 OR no API key → static lines only (randomly selected from seed pool, mood-filtered)
  4. Fact sheet assembly — per-NPC-type context built from PlayerContext snapshot. Analyst/anchor get top movers + breadth. Broker/trader get biggest movers. Analyst/broker get player portfolio. Trader gets recent trades. All get arc tone and event signals.
  5. Claude generation — system prompt injects NPC personality + CRITICAL RULES (only reference fact sheet, 1-2 sentences per line, stay in character). User prompt provides the fact sheet. Response: JSON array of 2-4 strings. Markdown fencing stripped if present.
  6. Cache — generated lines inserted into dynamic_npc_dialogue with metadata (npc_type, priority, trigger_source, entity_id, line_order).
  7. Static supplement — regardless of dynamic generation, some static lines are selected from static_npc_dialogue (filtered by derived market mood and phase) and also inserted into dynamic table for this date. This ensures there's always content even if Claude returns fewer lines than expected.

Unity: Fetching & Display

After generation completes (or fails gracefully), NPCBark.RefreshDialogue calls GET /dialogue?date=.... The backend returns a UNION of both tables for that date. Unity stores the results in two structures:

  • fetchedByType — Dictionary<string, List<string>> keyed by npc_type ("analyst", "broker", etc.)
  • fetchedAll — flat List<string> of all lines regardless of type

When a player approaches an NPC (within 2.5 units), NPCBark.PickRandomLine() uses this priority:

  1. Custom lines (if this NPC was spawned with specific lines)
  2. Type-matched lines (if this NPC has an assignedNpcType and matching lines exist)
  3. Any fetched line (fallback if no type match)
  4. Hardcoded fallback barks (25 ambient + market lines, for when backend is unavailable)

Unity: NPC Type Assignment

NPCSpawner uses NPCVariant[] — a serialized array configured in the Inspector. Each entry has a prefab reference, an npcType string, and a spawn weight. When spawning, PickWeightedPrefab() does weighted random selection (weight/totalWeight = probability). The selected type is passed through to NPCBark.Init(npcType: "analyst").

This means you can configure the city to be, say, 30% traders, 25% analysts, 25% brokers, 20% anchors — and each NPC will preferentially say lines matching their archetype. Visual differentiation (different prefab models per type) is optional but supported.

Knowledge Graph

The reactive knowledge graph is the thesis core. It's a directed graph of educational nodes with two unlock mechanisms: prerequisite completion (linear, for foundational concepts) and behavioral triggers (adaptive, for experiential learning). The claim is that delivering instruction at the moment of relevant experience produces better retention than sequential curriculum delivery.

Node Types

Knowledge Nodes (3)

Prerequisite-based. Form a linear chain: what_is_a_company → what_is_a_stock → market_buy_sell. Unlocked sequentially during onboarding. Auto-complete on dismiss. These are tutorial scaffolding — the player is explicitly taught before being set free.

Adaptive Nodes (11)

Behavior-triggered. Each has a trigger evaluator that checks player state. The player is never told "go do X to unlock Y." They trade naturally, and the system detects when their behavior has made a concept pedagogically relevant. The lesson arrives because they experienced it, not before.

Trigger Evaluation

Each trigger is a function: (entityId, gameDate) → bool. They run against the current DB state. Examples of what they check:

TriggerConditionUnlocks
portfolio_concentrationAny single ticker > 60% of portfolio valueDiversification node
first_losing_sellPlayer sold a position at a loss for the first timeLoss aversion / cutting losses node
bought_after_declinePlayer bought a stock that dropped >5% the previous dayBuy-the-dip behavior node
low_cash_ratioCash < 10% of total portfolio valueCash management node
market_wide_decline>70% of stocks declined today AND player has positionsSystemic risk node

Dynamic Content Generation

When a node unlocks, DynamicNodeContentService.GeneratePersonalizedContent() is called. It builds a prompt containing:

  • The node's concept name and static explanation (baseline content)
  • The trigger description (what the player did)
  • The player's full context snapshot (portfolio, concentration, recent trades, knowledge progress)

Claude generates 2-3 paragraphs connecting the concept to the player's actual situation. This is cached in dynamic_node_content per (entity, node) — if the player re-reads the node later, they see the personalized version, not the generic one.

Thesis connection: This is where all three layers converge. The game loop created the experience (player over-concentrated). The knowledge graph detected its pedagogical meaning (portfolio_concentration trigger). The LLM contextualized it ("You put 82% in NVDA, which just dropped 5%..."). One mechanism, three layers working together.

Game Loop & Day Cycle

The game simulates trading days during the 2007-2009 financial crisis. Each day has three phases with distinct player actions available. The day cycle creates temporal structure that drives both gameplay pacing and adaptive content timing.

Phase Mechanics

PhasePrice BasisPlayer ActionsBackend Events
Pre-MarketToday's OPENQueue orders, confirm (executes at open), read newspaper, check graphDialogue generation triggered, NPC spawning at 60% density
DayToday's OPEN (display)Explore city, walk near NPCs for barks, visit terminalsTimer-driven. No trades. NPC density 100%
Post-MarketToday's CLOSEQueue orders, confirm (executes at close), review daily summaryKnowledge triggers evaluated after trades. NPC density 30%

The "what you see is what you get" pricing rule is important: the player sees the open price during pre-market and gets that price. They see the close price during post-market and get that price. No slippage, no hidden mechanics. This is an educational tool — price transparency is a design constraint, not a simplification.

Arc System

Three arcs divide the 2007-2009 period into distinct difficulty/mood stages:

Bull Market

Apr–Oct 2007. ~130 trading days. Grading rewards growth. NPC tone: optimistic. Teaches basic mechanics when consequences are low.

The Unraveling

Nov 2007–Sep 2008. ~220 trading days. Mixed signals. Grading tightens. This is where hindsight becomes a trap — the player "knows" a crash is coming but not exactly when or how to position.

Meltdown

Sep 2008–Mar 2009. ~130 trading days. Survival mode. Break-even = S grade. The thesis argument: even knowing the historical era, disciplined risk management is still hard.

Arc grades (S/A/B/C/D) are based on return percentage with per-arc thresholds. Grade determines a cash multiplier carried into the next arc (S = bonus capital, D = penalty). This creates compounding consequences: early recklessness handicaps later arcs.
